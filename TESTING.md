# Registro de pruebas SnackCheck

Los casos se identifican como `TC-XXX`. El estado indica ejecución real, no diseño: se mantienen **Pendiente** hasta correrlos en n8n y registrar evidencia. Las pruebas de API en vivo pueden cambiar si Open Food Facts actualiza sus fichas.

| ID | Tipo | Caso y pasos | Resultado esperado | Estado |
|---|---|---|---|---|
| TC-001 | Funcional | Proporcionar al nodo 05 una respuesta controlada del nodo 04 con `statusCode: 200`, `body.status: 1`, Nutri-Score `e` y las tres mediciones presentes. Ejecutar desde el nodo 05. | `sufficientData: true`, `gradeVerdict: "no saludable"`, `verdict: "no saludable"`; los valores y semáforos coinciden con la entrada. | Aprobado |
| TC-002 | Integración | Ejecutar el workflow por su Test URL con `GET ?barcode=3017620422003` y consultar Open Food Facts en vivo. Revisar las salidas de los nodos 03, 04 y 08. | Open Food Facts responde con HTTP 200 y `body.status: 1`; el flujo devuelve HTTP 200, `ok: true` y datos del producto. Registrar Nutri-Score y veredicto observados, ya que la ficha puede cambiar. | Aprobado |
| TC-003 | Error | Enviar un barcode numérico confirmado como inexistente en Open Food Facts. Verificar antes el endpoint para evitar usar un código que se haya añadido posteriormente. Para una comprobación controlada, fijar la salida del nodo 03 con `body.status: 0` y repetir con `statusCode: 200` y `404`. | HTTP 404 con `PRODUCT_NOT_FOUND`; el mensaje indica que el producto no está registrado, pide comprobar el código de la etiqueta e incluye el ejemplo `?barcode=3017620422003`. La ejecución termina por la rama 04a, sin caída del workflow. | Aprobado |
| TC-004 | Error | Enviar `GET ?barcode=abc` (también puede comprobarse `123-45`). | HTTP 400 con `INVALID_BARCODE`; el mensaje solicita solo números, sin letras, espacios ni guiones, e incluye el ejemplo `?barcode=3017620422003`. Se ejecutan 01, 02 y 02a, sin llamar a Open Food Facts. | Aprobado |
| TC-005 | Error | Enviar GET sin parámetros de consulta y con el cuerpo vacío. Opcionalmente repetir con `?barcode=`. | HTTP 200 con `BARCODE_REQUIRED`; el mensaje indica que falta el código, pide enviarlo en el parámetro `barcode` e incluye el ejemplo `?barcode=3017620422003`. No se llama a Open Food Facts. | Aprobado |
| TC-006 | Error | Probar una respuesta controlada de producto encontrado con `statusCode: 200`, `body.status: 1`, Nutri-Score `unknown` y `nutriments` vacío o ausente. Se puede fijar la salida del nodo HTTP para hacer repetible el caso. | HTTP 422 con `INSUFFICIENT_NUTRITION_DATA` y el nombre del producto; el mensaje propone consultar otro producto con datos completos o completar la ficha en Open Food Facts e incluye un ejemplo de consulta. Los campos faltantes no se convierten en cero ni generan un veredicto; no se llama a la IA. | Aprobado |
| TC-007 | Rendimiento | Hacer 10 ejecuciones secuenciales de extremo a extremo en el mismo entorno y registrar duración total y duración de los nodos HTTP y Groq en **Executions**. | Nota de caracterización, no criterio de aprobación: reportar mediana, p95 y máximo. No hay SLA definido; el nodo HTTP de Open Food Facts tiene timeout de 10 s. | Aprobado |
| TC-008 | Error | Fijar la salida del nodo 03 con `statusCode: 503` y `body.status: 0`. Repetir con `statusCode: 200` y `body: {}` para simular una respuesta no válida. Ejecutar la rama del nodo 04. | HTTP 502 con `PRODUCT_LOOKUP_UNAVAILABLE` por el nodo 04a, no `PRODUCT_NOT_FOUND`. El mensaje indica un error o respuesta no válida de la API, aclara que no puede confirmar si el producto existe y propone reintentar con un ejemplo de consulta. No se calcula el veredicto ni se llama a la IA. | Aprobado |
| TC-009 | Error | En una copia de prueba del workflow, provocar un error de red en el nodo 03 usando una URL inaccesible o un timeout con una respuesta controlada que supere los 10 s. Ejecutar por el webhook con un barcode numérico. | La salida de error del nodo 03 llega al nodo 03a y devuelve HTTP 502 con `PRODUCT_LOOKUP_UNAVAILABLE`. El mensaje explica el fallo de conexión o timeout, indica que no es necesario cambiar el código y propone reintentar con un ejemplo. No se exponen detalles internos. | Aprobado |
| TC-010 | Error | En una copia de prueba del workflow, proporcionar datos nutricionales suficientes y provocar un fallo del servicio de IA, por ejemplo configurando en el nodo Groq un modelo no disponible. Ejecutar por el webhook con un barcode numérico. | La salida de error del nodo 07 llega al nuevo nodo 07a y devuelve HTTP 502 con `EXPLANATION_UNAVAILABLE`; no se ejecuta el nodo 08. El mensaje indica el fallo de la IA, propone reintentar sin cambiar el código, incluye un ejemplo y recomienda contactar con el responsable si persiste. No se exponen credenciales ni detalles internos. | Aprobado |

## Registro de ejecución

Al completar un caso, cambiar su estado a **Aprobado** o **Fallido** y anotar fecha, entorno, duración cuando aplique y enlace o identificador de la ejecución n8n. No guardar API keys, tokens ni datos sensibles en la evidencia.
